这个 Mock 平台眼下擅长的是"照结构造一份数据"：前端定义好字段，请求过来就按字段名推测语义、按类型递归生成一份随机响应，条件场景再挑一套返回。可它有个绕不开的短板——每次请求都是全新随机的一次性数据，跟上一次毫无关系。联调稍微复杂一点的场景就露馅了：前端刚 POST 建了一条记录，紧接着 GET 列表却看不到它；拿某条数据的 id 去请求详情，返回的又是另一批凭空生成的字段；删掉一条再查，它还在。真后端里"写完能读到、改完是新值、删了就没了"这种最基本的数据连续性，这个平台一点都给不了，前端只能对着一堆自说自话的假数据干瞪眼。

我们要补上的，是让某一类接口具备"有状态的资源集合"能力，把 Mock 端点从"每次现编"升级成"记得住、对得上"。

具体说，接口定义时可以把它标记成一个资源集合，并挑一个已定义的字段结构（可以直接复用现有的公共模型引用，也可以就地定义）作为集合里每条记录的形态。平台为这个集合在启动或首次访问时按该结构预先种入若干条记录——种入用的仍然是现在这套按字段名推测、按类型递归展开、多层模型引用照样展开的生成逻辑，不要另造一套假数据生成器。关键在于：这批记录一旦生成就固定下来，成为这个集合此刻真实的内容，而不是每次请求临时再摇一遍。

围绕这个集合，同一条资源路径上的不同方法要落地成真正对得上的读写语义，而不是各返回各的随机数据：

- 取列表要返回当前集合里实实在在存着的那批记录，且要支持翻页与按字段值做基本过滤，两次连着取（集合没被改动时）内容必须一致；
- 按 id 取单条要返回集合里对应那条的完整内容，id 不存在时给出结构化的未找到错误，而不是硬造一条或直接崩；
- 新建要把请求体里带来的字段真正并入集合、为新记录分配一个此后稳定不变的标识；请求体里没给全的字段，用同一套生成逻辑补齐，补齐后就固定下来；新建之后，取列表能看到它、按新分配的 id 取详情能读到它；
- 更新（整体替换与局部修改都要能表达）要精确改到目标那一条，改完之后再取，读到的是改过的新值，别的记录纹丝不动；
- 删除要把目标记录从集合里真正移除，删完再取列表少了它、再按 id 取详情给出未找到错误。

这里真正的难点不在于多写几个增删改查处理器，而在于跨请求的一致性必须始终成立，并且要作为正确性基准用测试锁定：任意一串"写—读"操作序列下来，读到的结果要如实反映此前所有写操作累计后的状态；记录的标识一经分配，在它被删除之前必须稳定，不能因为其它记录的增删而漂移或串号；同一条记录里那些"生成一次"的字段，在没有被显式更新时，历次读取必须给出完全相同的值，不能每次重新随机；并发地对同一个集合做多次写入时，不能出现标识重复、记录相互覆盖或计数对不上。此外还要提供一个把某个集合恢复到初始种子状态的手段，方便联调时反复重来；恢复之后，集合的内容要回到最初种入的那一批，就像从没被改过一样。

有几条边界要一并守住，别顾此失彼。资源集合是接口的一种新形态，原有那些普通接口、条件场景匹配、以及保存时的成环检测、路径合法性与"路径加方法"唯一性校验，全都不能因为这次改动而失效或改变行为——普通接口该怎么现生成还怎么现生成。集合形态与条件场景两者的关系要交代清楚并自洽：说明在一个资源集合接口上，条件场景与集合读写各自何时生效、谁优先，并让这套规则在实现里真正成立，而不是留下互相打架的模糊地带。资源集合所引用的字段结构如果涉及公共模型，成环检测的老规矩照样适用，不能因为走了集合这条新路就绕过成环拦截。集合里持有的状态要跟随平台既有的落地方式一起持久化，平台重启后集合内容与已分配的标识不丢失、仍然对得上（若原本采用的是服务自带的落盘方式，则按其一致的口径持久化即可）。

前端也要让这件事在浏览器里走得通：能把一个接口设成资源集合并选定其记录结构，能直观地对某个集合发起取列表、取详情、新建、更新、删除这几类请求并看到结果随着操作真实地变化（新建后列表里多一条、删除后少一条），能一键把集合恢复到初始状态。界面按职责拆分，不要把集合操作的交互和原有的接口/模型编辑挤成一大团。

工程上，跨请求的状态管理、集合读写的分发、与原有无状态生成路径的分流，要拆成边界清晰、可独立测试的模块，别把有状态逻辑硬塞进现在那个只管"选场景、现生成"的分发文件里。测试要覆盖这些点：一串混合的写读序列下最终状态正确；标识分配后保持稳定、不随其它记录增删漂移；"生成一次"的字段在未更新时历次读取一致；并发写入不产生标识重复或记录覆盖；恢复初始状态后集合回到种子内容；以及普通接口、条件场景、成环检测在改动后行为不变的回归。交付仍以容器化方式，一条命令把前端、后端与所依赖的存储一并构建启动，浏览器里能打开界面、对外能请求到这些带状态的 Mock 端点。
